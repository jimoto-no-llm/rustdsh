# DSH Web UI 軽量化 — Docker での A/B 計測

計測日: 2026-10-20 (JST)
ブランチ: `test/webui-lighter`
再現スクリプト: [webui-docker-bench.sh](../../scripts/webui-docker-bench.sh)

## 0. 結論

同一イメージ・同一 DSH・同一プロファイルで、変更点だけを変えた A/B。

| 指標 | 現行 | 修正版 | 差 |
| ---- | ---- | ------ | -- |
| 初回ロード転送量 (4資産, gzip) | **556,554 B** | **487,453 B** | **−69,101 B (−12.4%)** |
| `cache-control` | なし | `public, max-age=31536000, immutable` | 再訪問が実質ゼロ |
| 起動時間 (median, n=5) | 2,319 ms | 2,313 ms | −6 ms（有意差なし） |
| 初回ロード取得時間 (localhost) | 41.5 ms | 56.5 ms | **+15.0 ms（悪化）** |

**転送量は 12.4% 減るが、サーバ CPU は 1 ロードあたり約 15 ms 増える。**
localhost では純損失で、回線が概ね **37 Mbps より遅い場合に逆転して有利**になる
（69,101 B = 552,808 bit を 15 ms で割った値）。リモート接続や WAN 経由が主なら
明確な改善、ループバック専用なら体感差はない。

## 1. 計測条件

```text
image      : node:22-slim
             sha256:c3de60bf2f9dd0ac6370e6117950ff62d6e339527e7472301c9c78a017978392
node       : v22.23.3 (image), zlib 1.3.1-e00f703  (標準 zlib)
dsh        : 0.2.1-rc.2
host       : Linux 6.19.10 x86_64, 16 CPU, load 1.6–2.5
engine     : podman 5.8.9 (docker CLI 互換)
assets     : index-BxpfOGf3.css, index-CN7NIWNw.js,
             vendor-DV2921Zo.css, vendor-DcuzkuQH.js
```

**DSH_HOME は毎回まっさらに作り直し、コアバンドル2つだけを入れた。**

```json
"bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app"]
```

このマシンの実プロファイルは MCP サーバ 5 本と失敗プラグイン 3 本を含み、
起動時間が環境状態に強く依存する。それらを排除したことで、
**差分が変更点だけに帰着する**。ホスト側の計測で苦しんだ負荷ゆらぎも、
コンテナごとに起動し直す方式で消えている。

2 つのバリアントの違いは、テスト対象そのものだけ:

- **current**: 出荷設定のまま（`compressionLevel: 1`、キャッシュヘッダなし）
- **fixed**: webserver の `compressionLevel: 6` オーバーレイ + `rdsh-web-cache` プラグイン

コンテナはホストのネットワーク名前空間を共有する。DSH は
`--host 0.0.0.0` を「RCE の露出」として**明示的に拒否**するため、
ポート公開ではなく 127.0.0.1 バインドで直接叩いている。

## 2. 転送量（決定的・ばらつきなし）

5 ラウンドすべてで**バイト数が完全に同一**だった。圧縮結果は入力に対して
決定的なので、これは当然である。

| ラウンド | current | fixed |
| -------- | ------- | ----- |
| 1 | 556,554 | 487,453 |
| 2 | 556,554 | 487,453 |
| 3 | 556,554 | 487,453 |
| 4 | 556,554 | 487,453 |
| 5 | 556,554 | 487,453 |

```text
削減量: 69,101 B
削減率: 12.4%
```

### 2.1 zlib 実装差による baseline のずれ（重要な副産物）

ホスト側で測った現行値は 549,220 B で、コンテナの 556,554 B より 7,334 B 小さい。
原因は Node のビルド差だった。

```text
ホスト node v22.23.1 : zlib 1.3.1.zlib-ng     ← Fedora ビルド
コンテナ node v22.23.3: zlib 1.3.1-e00f703    ← 標準 zlib
```

同じ `index-CN7NIWNw.js` を同じレベルで圧縮した結果:

| level | ホスト (zlib-ng) | コンテナ (zlib) | 差 |
| ----- | ---------------- | --------------- | -- |
| 1 | 316,005 | 319,590 | +3,585 |
| 6 | 285,293 | 285,295 | **+2** |

**level 1 は実装依存で差が出るが、level 6 ではほぼ一致する。**
つまり今回の変更は「圧縮実装に依存しない側へ寄せる」効果も持つ。
削減率が環境で 11.2% / 12.4% と変わるのはこのためで、
どちらも正しい測定値である。

## 3. 起動時間（有意差なし）

コンテナ起動から `/assets` が 200 を返すまで。5 ラウンド交互測定。

| ラウンド | current | fixed | 差 |
| -------- | ------- | ----- | -- |
| 1 | 2,293 | 2,313 | +20 |
| 2 | 2,284 | 2,350 | +66 |
| 3 | 2,319 | 2,373 | +54 |
| 4 | 2,361 | 2,304 | −57 |
| 5 | 2,340 | 2,298 | −42 |
| **median** | **2,319** | **2,313** | **−6 (−0.3%)** |

固定が速い回数は 2/5 で、差の符号も両方向にばらつく。
**起動時間に有意差はない**（プラグインのヘッダ追加と level 6 設定は
起動経路に実質コストを足していない）。

## 4. 取得時間の悪化（正直なトレードオフ）

level 6 は圧縮率と引き換えに CPU を使う。同じ 4 資産を 10 回ずつ交互取得。

```text
current: 45 42 41 40 40 41 39 42 43 42   median 41.5 ms
fixed  : 62 56 55 59 56 58 59 56 57 55   median 56.5 ms
差: +15.0 ms (10/10 で fixed が遅い)
```

圧縮そのもののコストを直接測ると:

```text
level 1: 12.2 ms / 1ロード
level 6: 25.7 ms / 1ロード
        → +13.5 ms
```

取得時間の +15 ms はほぼこれで説明できる。
サーバは**リクエストごとに圧縮し直す**（圧縮結果のキャッシュはない）。

### 4.1 損益分岐

```text
削減 69,101 B = 552,808 bit
サーバ CPU 増 15 ms
損益分岐 = 552,808 bit / 0.015 s ≈ 36.9 Mbps
```

- **37 Mbps より遅い回線**（一般的なモバイル・WAN・VPN 経由）→ 明確に有利
- **それより速い回線**（localhost・LAN・光回線の実測値）→ ほぼ同等〜わずかに不利

このツールは通常ループバックで使うため、**体感では差が出ない**。
一方、リモートから繋ぐ使い方では効く。level を上げる判断は
「どこからアクセスするか」で決めるべきで、無条件の改善ではない。

## 5. キャッシュヘッダ（再訪問の効果）

```text
current: cache-control: (なし)
fixed  : cache-control: public, max-age=31536000, immutable
```

両方とも `ETag` は返さない（`etag_present=0`）。したがって現行は
再訪問のたびに 556,554 B を再転送する。修正版はブラウザが
再検証すら行わず、**その 4 資産については 0 バイト**になる。

これは導出であって実測ではない（HTTP クライアントはキャッシュしないため）。
実測で確認したのは「ヘッダが付与されること」と
「サーバは依然フルボディを返すこと」（repeat_request_bytes 319,590 / 285,295）
までである。ブラウザ実機での再訪問削減量は未計測。

```bash
cd /var/tmp/wt-uiperf

```

## 7. この計測の限界

- 4 資産のみを測っている。`index.html` は認証必須（401）で取得できず、
  プラグイン combo（14,653 B）も含めていない。したがって数値は
  **初回ロード全体ではなく、シェル資産 4 本の合計**である。
- コンテナ起動オーバーヘッド（約 0.3–1 s）を起動時間が含む。
  両バリアント同条件なので差の比較には影響しないが、絶対値は
  ホスト実測（約 3.5 s）と直接比較できない。
- `node:22-slim` は標準 zlib、ホストは zlib-ng。§2.1 のとおり
  現行側の絶対値が環境で変わる。
- ブラウザ実機での再訪問・FCP・LCP は未計測。ヘッダ付与までを実測した。
- ネットワーク帯域の制限（tc 等）は行っていない。§4.1 の分岐点は
  実測ではなく計算値である。
