# iOS 実機チェックリスト（#24 / #25）

この文書は**未実施の実機確認手順**です。headless Chrome / CSS fixture で確認できた範囲とは
別物で、ここに書いた項目はすべて「これから実機で確認する」ものです。チェックを付けた
人が、その端末・iOS バージョン・通知スタイルを記録してください。

- 対象: iPhone（Safari タブ / ホーム画面に追加した standalone）
- 前提: DSH は HTTPS で到達できること（Web Push と standalone は HTTPS が必要。
  `localhost` 以外の http では通知が許可されない）
- 記録から除外するもの: push endpoint、VAPID 鍵、購読 JSON、端末名・UDID・Apple ID、
  セッション本文。スクリーンショットはダミー文言のセッションだけで撮る。

## 前提: 2アプリのホスト実装（重要）

現行 host（rename 後）は push store を `$DSH_HOME/dsh-mobile-maxxing/push.json` に
置きます。実旧 `DSH-PWA` host は `$DSH_HOME/rdsh-pwa/push.json` を使うため、
**同じ `DSH_HOME` でも rename 後は同じ push.json ではありません**。危険なのは
次の条件です。

- **① 同じ push.json を旧 writer と共有した場合**: 旧 host は保存前 reload をせず、
  origin も無視して全購読へ送ります。片方の subscribe が他方の購読を上書き消失
  させ得て、二重通知にもなり得ます。symlink や手動コピーで store を共有させないで
  ください。
- **② 未移行の旧 namespace 購読**: `rdsh-pwa/push.json` に残った購読は本 PR では
  自動移行しません。新しい host からは見えないため、必要ならアプリで通知を
  再購読してください（手動 migration は別判断）。
- **③ テストの前提**: `notifications-issues.test.mjs` が確認するのは現行 rename 済み
  host 同士（同じ新 store への逐次書き込み）だけです。旧 host の writer や並行
  書き込み、旧 namespace からの移行は検証していません。
- 2つの現行 host なら同じ `DSH_HOME` で構いません。旧 host と併用する場合も、
  store file を共有しない限りは別 namespace のままです。共有が必要になったら
  `DSH_HOME` を分けてください。
- この整理は #28 の未完了事項で、Refs #28 として扱う。実機検証とは別。

## 共通の準備

1. 旧アプリ（例: 8444）と統一版アプリ（例: 8446）を、同じ `DSH_HOME` を見る2つの
   インスタンスとして起動しておく（どちらも現行 host）。**このチェックでは新規
   デプロイや再起動をしない**。上の①〜③を確認し、旧 writer と store file を共有
   しない（必要なら `DSH_HOME` を分ける）。
2. 両方をホーム画面に追加する（Safari の共有 → ホーム画面に追加）。
3. 両方で通知を許可する（iOS はユーザー操作からしか許可ダイアログを出さない）。
4. 設定 →「テスト通知」を各アプリで1回ずつ押し、下の表に結果を書く。

## #24 左端スワイプと「戻る」ジェスチャー

画面左端 36px 以内から右へスワイプしたとき、セッション一覧が開くか、Safari が前の
ページへ戻るか、両方が起きるかを確認する。開始位置を変えて3回ずつ試す。

| # | アプリ | 開始位置 | 一覧が開く | ページが戻る | 両方 | メモ |
| - | --- | --- | --- | --- | --- | --- |
| 1 | Safari タブ | 画面端 0–8px | ☐ | ☐ | ☐ | |
| 2 | Safari タブ | 20px 内側 | ☐ | ☐ | ☐ | |
| 3 | Safari タブ | 36px 付近 | ☐ | ☐ | ☐ | |
| 4 | standalone | 画面端 0–8px | ☐ | ☐ | ☐ | |
| 5 | standalone | 20px 内側 | ☐ | ☐ | ☐ | |
| 6 | standalone | 36px 付近 | ☐ | ☐ | ☐ | |

判定の目安:

- standalone は戻るジェスチャーが無い想定なので、#4–6 は「一覧が開く」だけなら期待どおり。
- Safari タブで #1–2 が「ページが戻る」または「両方」なら、競合が再現したことになる。
  iOS バージョン、ページのスクロール位置（最上部か途中か）、開始位置を記録する。
- 再現しても、この場で開始位置や CSS を推測で変えない。再現条件を Issue に追記して
  から対応を決める（#24 の「対応は別途判断」）。

## #25 Web Push の実表示

各項目を、旧アプリと統一版アプリの両方で確認する。

| # | 確認すること | 旧アプリ | 統一版 | 記録 |
| - | --- | --- | --- | --- |
| 1 | 設定の「テスト通知」でシステム通知が実際に表示される | ☐ | ☐ | 通知スタイル: |
| 2 | アプリを開いている間はアプリ内バナーになり、ack される | ☐ | ☐ | |
| 3 | アプリを閉じた状態でターン終了通知が届く | ☐ | ☐ | |
| 4 | 集中モード中でも通知スタイルどおりに表示される | ☐ | ☐ | 集中モード: |
| 5 | 通知をタップすると同じセッションが開く | ☐ | ☐ | |
| 6 | 「このブラウザから送ったターンも通知する」ON で、デスクトップ起点のターンも届く | ☐ | ☐ | |
| 7 | 同じセッションを両アプリで開いても、1つのターンで通知が二重にならない | ☐ | ☐ | |

二重通知の切り分け:

- 旧アプリからターンを開始 → 旧アプリにだけ届き、統一版には届かないこと。
- 統一版からターンを開始 → 統一版にだけ届き、旧アプリには届かないこと。
- 同じセッションを両アプリで開いたまま、どちらでもない起点（PC）のターンを
  「デスクトップ起点も通知する」ON で発生させる → 直近に host と話した側の
  アプリにだけ届くこと（#27 / #28）。両方に届いたら二重通知の再発。
- ホストを再起動した直後（どちらのアプリもまだ開いていない状態）でも、
  `webServer.getOrigin()` が保存済み購読の origin と一致すれば、そのアプリに届く。
  一致しない場合は推測せず送らない（全購読へのフォールバックは #27 で廃止）。
  届かなかったときはホストのログに
  `push skipped: no app origin has talked to this host yet` が出るので、
  「届かない」こととログの有無を記録する。アプリを一度開けば origin を学習し、
  以降は再起動後も届く。

## #26 質問カード / plan review（実機での補助確認）

自動テストは Chrome の CSS fixture で余白・折り返し・16px を確認しているが、実機の
Safari と実際の React カードは別途確認する。

1. ダミーの質問（`ask_user_question`）を1つ出し、カードの左右が画面端から 16px で
   あること、カード幅が画面幅 − 32px であることを確認する。
2. 選択肢に長い無改行トークン（URL など）を入れ、カード内で折り返して横スクロールが
   出ないことを確認する。
3. 自由入力欄をタップし、Safari が拡大しないこと（16px 指定）を確認する。
4. plan review カードでも 1–3 が同じであることを確認する。
