# コード修正の拡大比較計画

2026-10-19、拡大評価のモデル実行前に課題・集計方法を固定する。旧3課題の結果とカーソル反例は既知であり、今回の評価を完全な未見テストとは呼ばない。新規5課題と既知3課題を分けても集計する。既存結果を上書きしない。

## 標本と実行条件

- 評価8課題 × 3ラウンド = 24組、通常版と合成版で48ソルバー実行。
- 各ラウンドで同じTTL/LRU training課題から本家Harness²の`run_parallel(k=1)`によりハーネスを独立生成する。過去の合成版を使い回さず、非公開テスト・評価成績を改善へ渡さない。訓練は通常7セッション×3回、合計実行数は名目69セッション。不正な提案の本家規定の修正試行も別途記録する。
- 既知の並列map・ページ取得・依存順序に、区間差集合・増分フレーミング・階層設定マージ・再試行制御・CSV往復を追加する。全課題はソース2モジュール、公開2件。非公開は既存2課題が8件、ページ取得が9件、新規5課題が各10件で、1ラウンド75件。
- ページ取得の第9ケースは、初期`null`とNULを含む合法な5種類の文字列カーソルを区別する既知の反例。元の課題プロンプトを維持し、正解実装や特定の修正ヒントを加えない。
- 同じ`cursor-sdk / composer-2.5`、native rdsh、公開テスト実行権限、初期ソースを使用する。全ソルバーは新しい作業領域から開始し、24ステップ・600秒を上限とする。公開・非公開テストの上限は各15秒。
- 同時実行は最大2セッション。課題順を固定seedで決め、組内の通常版先行・合成版先行を均衡させる。seedは順序と統計集計用であり、SDKが公開していないモデル生成のseed・temperatureを制御したとは主張しない。
- 実行済み結果を保存し、再開時に再利用する。開始済みで結果がない処理を勝手に再課金して繰り返さない。成功したラウンドや課題だけを採用しない。合成案を採用できないラウンドも失敗として残し、通常版は評価する。

## 主評価と再現性

主評価は課題全体の成功率。native完了、実際の編集・テスト実行、編集範囲と公開テスト不変性、公開・所定件数の非公開テスト全成功を必要とする。計画した24組を分母とし、native失敗・ハーネス生成不能もend-to-end成功には数えない。採点拒否・採点器エラーは実装バグの不正解と区別して件数を示す。

副評価は非公開テスト通過率、カーソル回帰の成否、課題別・ラウンド別の改善と悪化、生成失敗率、公開テストのみでは検出できない不具合数。新規課題と既知課題も分ける。非公開テスト1件を独立したモデル試行として水増ししない。

同じ課題を繰り返し、同じラウンドでは1個のハーネスを共有するため、24組は完全な独立標本ではない。課題を単位とする不確実性と各ラウンドの差を示す。discordant pairのexact binomial値を出す場合は、独立性を仮定した探索的指標と明記する。全体平均が正でも、ラウンドごとの逆転や課題単位の回帰を隠さない。

過去3回の通常版のいずれかを非公開テストで正しく選べた場合のpass@3は、追加の参考上限として扱う。この選択には非公開oracleが必要であり、日常運用の自動再試行の実測とは呼ばない。

## 追加時間に見合うか

nativeセッションのwall time、起動を含むホスト計測、改善処理の追加セッション合計、事後採点時間、並列実行した全体経過時間を分ける。トークン数と金額をSDKが返さない場合はnullのままとする。

実験で観測した追加時間は、訓練の通常版1回を超えた追加処理と、評価時の合成版・通常版の時間差の合計とする。正味の追加成功数が正なら、その1件当たり追加秒数を示す。正味成功数が0以下なら、その比率を有用な改善効率として計算しない。

失敗を人が回復する時間を60・300・900秒と仮定した場合、成功増による回復時間の削減が追加実行時間を上回るかを条件付きで計算する。これは実際の人の修正時間を測った値ではない。ハーネスの再利用を8・24・100タスクに償却する場合も示すが、8課題外への品質の一般化は仮定である。各タスクごとに改善し直す費用と、固定版を再利用する費用を混同しない。

今回だけの推定利益、ラウンド間の符号の再現性、回帰、区間の不確実性から採用可否を判断する。少数課題で統計的に確実な品質向上や金銭的な得を断定しない。

## 採点の固定と検証

新規課題は独立した一時参照実装で公開・非公開テスト全件の成立を確認する。参照コードをモデル領域や改善用証拠へ置かない。既知カーソル反例も主評価の実行前にスイートへ固定する。

旧採点器が正当な`RegExp.test()`やコメント中の単語を拒否する問題は、評価前に構文木による検査へ修正する。OS sandboxの権限は変更しない。訓練開始時と最終評価時のハッシュを保存し、この採点器変更を明示する。生成ソースの採点操作も独立に点検する。構文検査と同じJavaScript環境での実行を、任意の敵対的コードへの完全な採点隔離とは主張しない。

## 評価中の仕様監査による追加分析

設定マージの最初の結果が入り始めた時点で、プロンプトのordinary objectをplain object限定と読む余地がある一方、非公開テストはカスタムprototypeのレコードのown keyを処理する契約であると判明した。これは評価開始後に見つけた仕様解釈の問題であり、事前定義の主評価を置き換えない。

元の8課題24組を変更せず保存し、設定マージを除く7課題21組の感度分析を併記する。追加で`coding-config-clarified-tasks.json`の明確化したプロンプトのみを使用し、同じ訓練済み3ハーネスと同じ公開・非公開テストで両版を3組6セッション追試する。モデルが生成したソースを修正せず、ハーネスの生成・選択もし直さない。レコードの定義と継承キーを無視する契約を明確にし、テスト自体は変更しない。

この追試は事後の補助分析として表示し、標本数を30組の独立な新規課題へ水増ししない。実験全体の実行回数と時間には追試6セッションを含め、運用費用の推定では同じ訓練済みハーネスの生成費用を二重計上しない。
